# [tool-feedback] mesh3d accepts a ship mesh that leaves holes on screen

- Tool: tools/mesh3d (new in this take; not in the law 66 tool list)
- Tool version / commit: `a611406` on branch `cursor/ship-real3d-b4da` (parent `408aa75`)
- Take / branch + commit: ship real-3D proof, `cursor/ship-real3d-b4da`
- Defect seen on screen: the 720×1600 orbit shows a recognizable crashed ship with holes through the hull. Uncovered texels are transparent, which is what the golden rule requires, and the build still prints `PASS`.
- Tool metric vs measured: the build records `triposr.alignIoU` 0.445 and accepts any mesh at or above 0.15. Screen coverage of the above-ground surface is mean 0.703, minimum 0.618 (`coverageByYaw` in `tools/mesh3d/out/qc/report.json`). The face flag 0.762 does not test facing. The four-view visual hull on the same cameras scored silhouette IoU 0.543 and was not the shown mesh. Max magnification 0.976 is a real measurement and stayed ≤ 1.
- Reproduce: `python3 tools/mesh3d/build.py --views tools/mesh3d/inputs/ship --out tools/mesh3d/out --engine auto` then open `tools/mesh3d/out/frames/yaw-090.png`.
- Still / screenshot: `tools/mesh3d/out/frames/yaw-090.png` and `tools/mesh3d/out/contact.png`
- Short video: `tools/mesh3d/out/orbit.mp4`
- Proposed fix: when both meshes exist, show the one with the higher silhouette IoU, and print the coverage minimum next to any completion line so a holey orbit is not read as a clean pass. No new hang threshold in this take.
